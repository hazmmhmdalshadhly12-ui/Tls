# Changelog

All notable changes to **HAZEM Tunnel** are documented here.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [1.2.1] — 2026-10

### Fixed — installer payload & packaging robustness
v1.2.0's MSI was technically valid (its cabinet passed independent integrity tests), but
some users hit *"The cabinet file 'cab1.cab' required for this installation is corrupt
and cannot be used"* — caused by an interrupted download of a single-file 61.5 MB cabinet.
v1.2.1 removes that failure class and upgrades the install model:

1. **Full program-folder install.** The MSI now installs the complete self-contained
   folder (278 files: `HAZEM.Tunnel.exe`, `hostfxr.dll`, every runtime library) into
   `%ProgramFiles%\HAZEM Tunnel` — the way normal Windows programs install. v1.2.0's MSI
   shipped a single-file EXE that had to extract itself to `%TEMP%` on *every* launch
   (slow start, antivirus friction). The installed app now runs straight from
   Program Files with zero TEMP extraction.
2. **MSZIP cabinet compression** replaces the default LZX: the most conservative,
   universally supported MSI codec, decoded by Windows Installer's own built-in paths.
3. **Explicit component authoring.** The MSI source is generated by
   [`installer/msi/gen_wxs.py`](installer/msi/gen_wxs.py) (one component per file,
   deterministic, reviewable) instead of relying on undocumented harvesting behavior.
4. **Close-on-install.** A running `HAZEM.Tunnel.exe` (installed or leftover portable
   copy) is closed automatically during install/upgrade — no "file in use" or reboot
   prompts can block setup anymore.
5. **Release-time integrity proof.** The release workflow uploads the exact publish
   folder as a build artifact, and every released MSI/zip is download-verified
   (SHA-256 + full cabinet extraction, file-by-file byte comparison) before being
   announced. Verify your own download with the attached `.sha256` files:
   `certutil -hashfile HAZEM-Tunnel-1.2.1-setup.msi SHA256`.

### Changed
- `scripts/publish.ps1` now produces both layouts from one invocation: the full folder
  (MSI payload) and the single-file portable EXE (zip), both without PDB files.
- App/version assembly metadata bumped to 1.2.1 (About page reflects it automatically).

## [1.2.0] — 2026-10

### Fixed — startup crash: DI composition was never validated
v1.1.0 crashed at startup on a clean machine with:

> *Unable to resolve service for type 'HAZEM.Tunnel.Core.Interfaces.ITunnelEngine'
> while attempting to activate 'HAZEM.Tunnel.App.ViewModels.DashboardViewModel'.*

Root cause: the ViewModels depend on **interfaces** while the composition root registered
only **concrete classes**, and several services were never registered at all. A full audit
found seven broken/missing registrations that would have crashed one after another:

1. `ITunnelEngine` — only concrete `TunnelEngine` was registered (the reported crash).
2. `ISshConnector` — only concrete `SshConnector` (Servers page).
3. `IDialogService` — only concrete `DialogService` (used by five pages).
4. `IHealthChecker` — only concrete `HealthChecker`.
5. `InMemoryLogProvider` — never registered (Logs page).
6. `ILoggerFactory` / `ILogger<T>` — never registered (used by the profile store and every ViewModel logger).
7. `TunnelSettingsViewModel` — never registered (MainViewModel composes it).

Fixes:

- **Composition root extracted** to [`AppComposition`](src/HAZEM.Tunnel.App/Services/AppComposition.cs) —
  every interface used by a ViewModel now aliases the same shared singleton.
- **New 4th test project** [`HAZEM.Tunnel.App.Tests`](tests/HAZEM.Tunnel.App.Tests/) builds the REAL container
  (`ValidateOnBuild` + `ValidateScopes`) and resolves every ViewModel, asserts the interface
  aliases are shared singletons, and exercises the proxy credential checker. A missing
  registration now fails CI instead of shipping.
- **Fail-fast startup**: the container is built with `ValidateOnBuild` before any window is
  shown; if composition fails, a plain message names the problem, points to the log folder
  (opened automatically) and exits cleanly — no cryptic mid-activation dialogs.
- `About` page version is now read from the assembly version instead of being hard-coded.

### Added — real Windows installer
- **MSI installer** (`HAZEM-Tunnel-<version>-setup.msi`, WiX 5): installs into
  `%ProgramFiles%\HAZEM Tunnel`, Start Menu + desktop shortcuts, *Apps & features* entry
  with icon, major-upgrade aware, clean uninstall (user data preserved).
- The release workflow now builds the MSI on `windows-latest` for every `v*` tag and
  attaches it (with a `.sha256` checksum file) to the GitHub Release next to the portable zip.
- `scripts\build-installer.ps1` builds the same MSI locally on Windows.
- The Inno Setup script got a **valid AppId GUID** (the old one contained non-hex
  characters) and the current version.

## [1.1.0] — 2026-10

### Fixed — startup log error dialog
v1.0.0 could show an error dialog at startup when the log file was momentarily held by
another process (second app instance, antivirus scan, log viewer):

> *The process cannot access the file `…\logs\hazem-*.log` because it is being used by another process.*

The file logger threw during rotation/reopen and the exception surfaced into the UI.
Fixed at four levels:

- **The file logger can never throw.** All file I/O is guarded; on failure it degrades
  silently (sidecar file → drop) instead of surfacing an exception into the app.
- **One persistent log stream**, opened with `FileShare.Read`; rotation happens under the
  same lock as writes — no reopen races.
- **Single-instance mutex.** A second launch now shows a friendly message instead of
  fighting over profiles/credentials/log files (the most common trigger).
- Global exception handlers **ignore logging failures** — they can no longer pop the
  error dialog even if something else in the logging pipeline changes.

### Added
- `.gitignore`, CI workflow, issue templates, community files (LICENSE / SECURITY / CONTRIBUTING / CHANGELOG).

## [1.0.0] — 2026-10

### Added — first public release

**Transports**
- TLS with explicit SNI control (dial endpoint and SNI hostname kept separate on purpose).
- SSH (SSH.NET): password or PEM private key; host-key policies TOFU / Strict / Pinned.
- SSH-over-TLS bridge — two encrypted layers in one connection.
- WebSocket (`ws://` / `wss://`) with configurable path and headers.

**Local proxy**
- SOCKS5 server (RFC 1928) with optional username/password auth (RFC 1929), CONNECT only.
- Binds to `127.0.0.1` by default; LAN binding is opt-in with an explicit warning.

**Desktop app**
- WPF (MVVM, dependency injection), .NET 10, self-contained win-x64 single-file publish.
- Dashboard with staged connect flow: proxy → transport → through-tunnel health check → Connected.
- Real byte counters and rates — no fabricated statistics anywhere.
- Versioned JSON profile schema (v1) with import/export; sample profiles included.
- Secrets stored via Windows DPAPI; profiles reference them by opaque key only.
- Redacted rotating file logs with retention cleanup.
- In-app update-safe single instance; health check gates the "Connected" state.

**Quality**
- xUnit test suites across 3 projects (84 tests) including live loopback suites.
- Zero-warning build policy (`TreatWarningsAsErrors`).
- Scripts: `scripts/build.ps1`, `scripts/test.ps1`, `scripts/publish.ps1`.
- Docs: config schema, manual QA checklist, honest build report.
